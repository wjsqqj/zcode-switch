# z.ai 登录辅助条改为同页表单切换

## Goal

z.ai 登录窗口的注入式辅助按钮条（手机号 / Google / GitHub / 邮箱登录 / 邮箱注册）要在
「邮箱与手机号在同一个页面、手机号表单默认隐藏」的真实结构下正确工作，不再出现误报和错跳。

## Background（用户实测反馈）

1. 打开登录页 → 点「手机号登录」：能到手机号表单（上一版已修好，不能回归）。
2. 点「GitHub 登录」跳到 `github.com` 授权页后，再点「邮箱登录」→ 提示「已在邮箱登录页」（实际人在 GitHub 页）。
3. 同一时刻点「手机号登录」→ 整页跳回登录页，落地后显示的是**邮箱**表单，看起来像「跳到了邮箱登录页」。

根因（代码层面，不改需求只记录）：

- 注入脚本不判断当前域名，在 GitHub 页面上仍按 z.ai 页面的文案特征做判断；GitHub 登录页的
  `Forgot password?` 命中「登录表单特征」，于是误报「已在邮箱登录页」。
- 找不到手机号入口时无脑 `location.href = 授权入口`，落到默认展示邮箱表单的登录页，而自动补点
  只认「Google 按钮的前一个图标」这一种旧结构，补点失败。
- 脚本把手机号/邮箱当成**两个不同页面**，而实际是同一页面的两个表单（手机号默认隐藏），没有
  「当前可见的是哪个表单」与「页内 tab 切换」的概念；可见性只靠 `offsetParent`，判不准隐藏面板。

## Requirements

- R1 页内切换优先：邮箱 / 手机号按钮首先要能在**同一页面**内把表单切过来，不产生整页跳转；
  只有当前页确实没有可切换入口时才允许整页跳转。
- R2 表单归属判定要可靠：以「当前可见的输入框类型/占位符」判断页面正显示邮箱还是手机号表单，
  而不是靠页面里出现的中文/英文文案猜测；隐藏面板里的文案不得参与判定。
  「已在某页」的提示只在目标表单**确实已经可见**时出现。
- R3 第三方页面不得误判：停在 GitHub / Google 等 z.ai 之外的域名时，不得拿对方页面文案做判定、
  不得给出「已在邮箱登录页」这类误报；此时邮箱 / 手机号按钮的语义就是「整页回到 z.ai 登录入口」。
- R4 整页跳转后必须自动落到目标表单：跳转前记住意图（邮箱登录 / 邮箱注册 / 手机号登录），落地后
  自动补点切换到目标表单，补点逻辑与 R1/R2 使用同一套判定，不能只认某一种旧 DOM 结构。
- R5 既有能力不得回归：Google / GitHub 按钮、授权确认页自动点「授权」、多次注入幂等（同一页面重复
  注入不得叠加多个轮询）、登录成功后的接力取码流程不变。
- R6 文案新增「已在手机号登录页」需中英文齐备（Rust 侧 i18n 表）。
- R7（第 2 轮实测追加）跳转意图必须能跨过第三方域：登录入口落地默认就是邮箱表单，所以从 GitHub 页回跳时要切手机号表单，
  意图必须随跳转一起带过去（sessionStorage 按 origin 隔离，在 github.com 写的值到 chat.z.ai 读不到）。

## Constraints

- 改动集中在 `src-tauri/src/oauth.rs` 注入脚本 + `src-tauri/src/i18n.rs` 文案；不新增依赖、不改
  OAuth 协议流程与接力判定（`lib.rs` 只做必要注释）。
- 注入目标是外部 https 页面（WebView2 / Chromium），脚本必须 ES5 语法、单个 IIFE、幂等。
- 无法在本机自动化验证真实 z.ai 页面 DOM，判定必须写成「多重探测 + 逐级降级」，不能押在单一选择器上。

- [x] AC5 手机号表单已可见时点「手机号登录」→ 提示「已在手机号登录页」。
- [x] AC6 Google / GitHub 登录、授权确认页自动授权、登录完成后接力取码均照常工作；同一页面重复注入
      不产生多份轮询或重复点击。

## Out of Scope

- 不改「授权登录走代理」逻辑、不动额度查询 / 领取 / 切换链路。
- 不重做登录窗口 UI（按钮条样式保持现状）。
