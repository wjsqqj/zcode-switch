# 领取刷新卡死修复与活动中心（父任务）

## Goal

收敛 2026-10-26 用户反馈的「刷新卡死 + 活动不可见」问题，交付两个可独立验收的成果：让领取刷新在任何异常下都能给出明确反馈并自动恢复；让活动具备开始时间、主动探测与详情查看能力。

## 背景（用户原话归纳）

- 点击 `tcaiq772` 行内刷新 → 行内提示「已领取过 ZCode 1024 Dev Day」，随后一直处于刷新态不恢复。
- 点击 `旅行者1423` 行内刷新 → 无任何提示，同样一直刷新。
- 行内 ↻ 再也不能点第二次；顶部「刷新」点击无任何反应；自动领取也查不到资格。
- 整个窗口最终卡住，切换账号、设置等其他按钮也点不动。
- 额度区一直显示「查询中…」。
- 活动「ZCODE GLOBAL BUILD GLM-5.3-Flash 3亿 至 10/27 09:00」缺开始时间；用户不知道活动何时出现，希望有开关主动探测，并能点开看详情。

## 现场事实（2026-10-26 实测，用于校正判断）

- `--cli claim-preview`：`tcaiq772` 2.9s 返回 0 个可领；`旅行者1423` 1.0s 返回 0 个可领 → **后端单次请求不慢，也不挂起**。
- `claim-history.json`：`tcaiq772` 领过 `ZCode 1024 Dev Day`；4 个账号领过 `ZCODE GLOBAL BUILD`（今日 19:19）。
- `settings.json`：`auto_claim: false`。
- 代码侧三处「点了没反应」：`refreshClaim()` / `acctRefreshClaim()` / `claimAll()` 在全局忙时**静默 return**；每账号刷新后 60s 冷却；全局刷新账号间隔硬等 5s（6 账号 ≈ 40s）。
- 两处「整窗卡死」机制：前端 `render()` 无 try/catch（抛异常即整页停在旧帧，而旧帧恰好是 busy 态）；后端 `claim_refresh` / `get_account_quota` 等 `async fn` 内直接执行阻塞 ureq（激活 2×10s + preview 25s + marketing 25s），并发点击会占满异步运行时工作线程，`get_state`、`set_behavior` 等全部排队。

## 子任务拆分

| 子任务 | 目录 | 负责 |
|---|---|---|
| A 刷新状态机修复 | `.trellis/tasks/10-26-claim-refresh-state-fix` | 前端状态机与反馈、后端阻塞 I/O 整改、render 异常兜底、3012 风控 mock 矩阵 |
| B 活动中心 | `.trellis/tasks/10-26-claim-activity-center` | 活动开始时间、活动探测开关、**顶部「活动」按钮 + 汇总弹框（可领/已领取/已过期）+ 行内活动条快捷** |

依赖顺序：A 先做（B 的活动探测复用 A 的请求通道与错误兜底），B 在 A 收口后开始。

## 跨子任务验收标准

- [ ] 任意一次刷新（单账号/全部/自动）结束后 1s 内，界面所有刷新入口恢复可点，或明确显示剩余冷却秒数。
- [ ] 任何被拒绝的点击都有可见反馈（toast 或界面文案），不存在静默 return 路径。
- [ ] 并发触发 3 个账号刷新时，窗口内其他操作（切换账号、打开设置、查看详情）仍可响应。
- [ ] render 抛异常时界面出现可见错误条且可继续操作，不再整页冻结。
- [ ] 活动详情与开始时间在真实账号上可见；探测默认关闭，开启后按约定节流。
- [ ] 后端 `cargo check` 0 warning；mock 风控矩阵包含 3012 unusual activity 用例且全绿。

## 非目标

- 不改变领取协议（`billing/claim` + 阿里云验证码）与账号切换语义。
- 不新增独立「活动」页面（只做行内活动条 + 弹框）。
- 不做服务端没有的时间字段的猜测性编造。
