# 活动中心：开始时间 / 探测开关 / 详情弹框（子任务 B）

> 父任务：`.trellis/tasks/10-26-claim-refresh-activity-overhaul`
> 依赖：子任务 A（复用 `invokeWithTimeout`、`refreshGate`、`#err-bar` 错误兜底）

## Goal

让用户能看到「活动什么时候开始/结束、具体是什么、哪些账号能领」，并能在新活动出现时被主动提醒，而不是靠反复点刷新碰运气。

## 现状（2026-10-26 实测）

- 活动条只显示奖励摘要与结束时间（`claim.untilDate`），**没有开始时间**。
- `billing/current` 已返回 `starts_at` / `ends_at`（`claim::fetch_active_plans` 已解析），前端 `claimedStripHtml` 只用了 `ends_at`。
- `marketing/touch` 的 delivery 经 `walk_marketing_delivery` 宽松扫描成 `ClaimPlan`，`campaign_id`、banner/popup 文案、按钮动作被丢弃，前端拿不到详情。
- 没有「探测活动」能力：只有手动刷新才请求上游。

## 需求决策（2026-10-26 用户确认，含一次改版）

- **入口（改版）**：顶部工具栏新增显式「活动」按钮作为主入口，带**可领活动数**角标；点击打开**汇总弹框**（分组：可领 / 已领取 / 已过期），点单条展开完整详情。行内活动条**仍可点击**作为快捷路径（`title` 提示「点击查看活动详情」）。**不新增独立页面/路由**。
- **无活动时**：按钮仍显示但置灰，点击提示「暂无探测到活动（可在设置里开启活动探测）」——保证入口可发现。
- **探测**：默认**关**；开启后每 **30 分钟**随机挑 **2 个账号**（可用账号不足 2 个则全量），只请求 `marketing/touch`，不领取、不写历史、不触发 activation。
- **探测抖动（防脚本特征，2026-10-26 追加，含 20min 调整）**：
  - 活跃窗口 `16:00–次日 12:00`（用户配置，默认值）内轮次间隔 = `20min + U(0, 5min)`（秒级随机，永不落在整分钟/整 20 分钟边界）；
  - 两个账号各自再独立取 `0–5min` 随机延迟下发，且**串行**（第二个账号在前一个完成后再随机 `20–90s`）；
  - 账号级最小间隔 **60 分钟**（6 账号 × 每轮 2 个 → 单账号约每 67min 被抽一次；账号少于 3 个时自动退化为 60min 一次）；
  - 非活跃时段 `12:00–16:00`：每账号最多 3 小时一次；
  - 配额：**每账号每日 ≤ 20 次**（全局约 ≤ 106 请求/天）；**达配额后降频到 3 小时一次，不停止**（避免活动来了却没探测）；
  - **窗口不在前台（后台）时不探测**，回到前台后补一次（带随机延迟）；最坏发现延迟 ≈ 25min。
- **提醒**：探测到新活动 → toast + 直接打开该活动详情弹框；同一活动不重复提醒。
- **到点提醒（2026-10-26 追加）**：对已获得的活动分别注册两个时间点提醒——① 活动开始（`plan.starts_at`）② 待生效生效（`entitlements[].effective_at`，如今天 23:00）。各提醒一次，形式同为 toast + 打开详情弹框。
- **到点自动领取（2026-10-26 追加，默认关）**：新增「到点自动领取」开关，**依赖「自动领取」已开**；到 `effective_at` 后随机 5–30s 触发一次自动领取尝试。需人工验证时会弹出验证码窗口（非全自动，必须说明）。
- **开始时间**：优先 `billing/current.starts_at`；活动 payload 若有则同样展示；两者都无 → 显示「未提供」，**不编造**。
- **生效时间（2026-10-26 实测修正）**：`plan.starts_at` ≠ 生效时间。真实生效时间在 `entitlements[].effective_at`（样本：`ZCODE GLOBAL BUILD` `starts_at=19:15:53` / `effective_at=23:00:00` / `ends_at=次日 09:00`）。界面必须分别展示「活动开始 / 待生效 / 结束」，不能把 `starts_at` 当生效时间。

## Requirements

- R1 **开始时间展示**：活动条、已领取条、详情弹框都显示开始时间与结束时间；缺失显示「未提供」。
- R2 **活动入口**：顶部「活动 (n)」按钮 + 汇总弹框；无活动时置灰 + 点击说明原因。
- R3 **详情内容**：活动名、`campaign_id`、`plan_id`、时间窗、奖励列表（名称/额度/周期）、banner/popup 文案、按钮动作（`action.type` + `plan_id`）、所属账号与状态。
- R4 **探测开关**：设置项「活动探测」默认关，持久化到 `settings.json`；开启后按 R4.1 的调度策略执行，每次最多 2 个账号。
- R4.1 **探测调度与配额**：活跃窗口 `16:00–12:00` 内轮次 `20min + U(0,5min)`；账号独立随机延迟后**串行**下发（间隔 `20–90s`）；账号级最小间隔 60min；`12:00–16:00` 降频至 3h/账号；每账号每日 ≤ 20 次；**达配额降频到 3h 一次而非停止**；后台不探测、回前台补一次。
- R4.2 **账号级静默（2026-10-26 追加）**：某账号一旦探测到「仍在有效期内」的活动（`ends_at > now` 或 `effective_at` 未到），该账号**暂停自动探测直到该活动 `ends_at`**；活动结束自动恢复常规频率。静默状态持久化（`localStorage["zsw-activity-known"]`），重启后不重新全量探测。
  - **手动优先**：用户点顶部「活动」按钮或手动刷新时，静默期账号仍强制探测一次（用户显式意图，且不产生自动请求）。
  - 已知取舍：完全静默期间若服务端给同一账号补发**第二个**活动，将探测不到，直到第一个活动结束或用户手动刷新。
- R5 **探测纪律**：只走 `marketing/touch`；失败静默（`flowlog` 记录）；命中 3012 走既有 `risk` 退避且冷却账号跳过；不产生 `billing/claim` 请求、不写 `claim-history.json`。
- R6 **新活动提醒**：本地已见集合（`accountId|campaignId|planId`）去重；首次出现 → toast + 详情弹框。
- R6.1 **到点提醒**：对已知活动注册 `starts_at`（活动开始）与 `effective_at`（生效）两个提醒，各一次；去重键含时间点类型，避免与 R6 重复。
- R6.2 **到点自动领取**：开关默认关、依赖「自动领取」已开；到 `effective_at` 后随机 5–30s 触发一次自动领取；需验证码时弹窗（非全自动，UI 必须写明）。
- R6.3 **提醒可靠性**：系统休眠/时钟跳变后，用 60s ticker 比对时间戳补偿，禁止只依赖长 `setTimeout`。
- R7 **数据承载**：在 `ClaimPlan` 上以**可选**字段携带活动元数据（`campaign`），不破坏既有字段与领取流程；`ClaimGrant` 增加 `effective_at`。
- R8 **零回归**：可领列表、领取流程、`claimHold`、风控判据不变；i18n zh/en 同步。

## Constraints

- 不新增独立页面/路由；弹框复用现有 modal 风格（参考 `openProviderModal`）。
- 探测只在主窗存活时进行，不做后台常驻任务；不新增网络依赖（沿用 `ureq` + 既有超时）。
- 后端所有上游请求必须经 `run_blocking`（见 `claim-plans.md` §12.1）。

## Notes

- 实测样本：`wjsqqj` 的 current 返回 `starts_at=2026-10-26 19:15:53`、`ends_at=2026-10-27 09:00:00`，可作为真机验收基准。
- 「随机 2 个账号」用于把单账号探测频率压到平均 90 分钟一次，同时避免 6 个账号同时打上游触发风控。
- 服务端不下发活动（如 tcaiq772 / 旅行者1423）时，界面应能明确表达「该账号当前无可用活动」，并区分于「请求失败」。
